# Org-bound commands

Some `fs-forge` commands talk to a GitHub org: they read its claims repo (`<org>/claims`) and its state repos, or they write to them. Reads need `GITHUB_TOKEN` and `--org`. Writes happen only with `--commit`, which creates a branch, dispatches a provisioning workflow and lets that workflow open and merge PRs. This map keeps every org-bound drive opt-in against an org the user names.

## Sub-features

- `ob-no-org` shows each command refusing to run with no org named (offline, safe to run).
- `ob-guards` shows `drive.sh` refusing `--commit` and unnamed orgs before anything runs (offline, safe to run).
- `ob-defaults` reads the org's defaults: `defaults list`, `defaults show <kind>`, `defaults apply`.
- `ob-discovery` reads the org's claims: `discovery map` and `discovery org-elements`.
- `ob-preflight` checks whether a create, edit or delete of a repo, team, user or tfworkspace would collide with existing state.
- `ob-watch-checks` watches the check runs of a claim's wet PRs.
- `ob-edit-read` and `ob-features-read` read a claim from the org with `edit REFERENCE --diff` and `features list <component>`.
- `ob-delete-dry-run` runs `delete` without `--commit`.
- `ob-write` covers the paths behind `--commit`: `create`, `edit`, `features add|edit|remove` and `delete`.
- `ob-teardown` runs those claims back out with `delete --commit` and proves the org is clean with seven `gh api` checks; the recipe is `$V/fixture.sh teardown`.
- `ob-audit-issue` covers `--issue` and `--create-issue` on those `--commit` paths, in a `write` drive.

## How to get to it (user POV)

- Run `fs-forge defaults list|show <kind>|apply [<Kind>-<name>]`, `fs-forge discovery map|org-elements`, `fs-forge preflight --kind <kind> --name <name> --create|--edition|--deletion`, or `fs-forge watch-checks <Kind>-<name>`, each with `--org <org>` or `FSCRT_ORG`.
- Run `fs-forge edit <Kind>-<name> ... [--diff]` or `fs-forge features add|edit|remove|list <component>` with no `--file`.
- Run `fs-forge delete <kind> <name>` to see what a delete would dispatch, and add `--commit` to dispatch it.
- Add `--commit` to `create`, `edit` or `features add|edit|remove` to publish the change.

## Driving it with drive.sh

Preconditions:

- `DOCTOR OK`, and `$V/doctor.sh --org <org>` for every drive below except `ob-no-org` and `ob-guards`.
- For every drive below except `ob-no-org` and `ob-guards`: the user has named the org in this conversation and agreed to the drive. Do not take the org from `FSCRT_ORG`, from `gh`'s defaults or from a fixture. `ORG` below stands for that org.
- A token, picked in `gh`'s order: `GH_TOKEN`, then `GITHUB_TOKEN`, then `gh auth token`. `drive.sh` passes it to the child only in `read` and `write` modes and fails the drive when it finds the token in the evidence, redacting it from every matching evidence file before reporting.
- For `ob-write`: `ORG` is a pre org registered under `firestartr-pre/app-firestartr` at `kubernetes/firestartr-pre/<org>/` (see `smoke-test-renderer`), and the user approves each `write` drive by name. Run `publish-cli-snapshot-on-pre` first if the workflow must run this branch's CLI.
- `ia-test` claims come from `$V/fixture.sh setup --org ORG --id ID`, which writes and validates them under `$FSF_HOME/fixtures/ORG/ID/`. `$V/fixture.sh teardown --org ORG --id ID` deletes them through `drive.sh --mode write`, sweeps their leftover `fsf-verify-grp-<id>`/`fsf-verify-cmp-<id>` branches, PRs and issues, and proves the org clean with seven `PASS` checks: claim files, branches, PRs, state CRs, repo, team and issues. It refuses any org not registered under `firestartr-pre/app-firestartr`. When a delete stops before its deletion PR merges, teardown keeps that PR open (closing it would throw away the only way forward), prints `HUMAN: merge <url> once PR Verify is green, then rerun teardown` and the rerun command, and exits 1.
- `read` mode was exercised live against `pre-vieitesss`. So were these `write` paths, on `firestartr.dev/ia-test` claims from `$V/fixture.sh setup`: `create`, `edit`, `features add|edit|remove --commit`, `create --commit --create-issue` and both `delete` legs — `delete component --commit --issue <n>` then `delete group --commit`, each exit 0 with `"status":"ok"` and its deletion PR merged, after which `$V/fixture.sh teardown` reports seven `PASS` and `TEARDOWN OK`. That needs `claims_repo` >= 3.2.0 in the org's `claims` repo: on 3.0.1 `unprovision-claim.yaml` merged the deletion PR without waiting for its `PR Verify` and failed at `Merge claims PR` with `Merge state: UNSTABLE`, leaving the PR for a human. 3.2.0 adds `Wait for PR Verify (claims PR)` before `Merge claims PR`. Pin the upgrade on the `claims` ComponentClaim with `features edit claims --name claims_repo --version 3.2.0 --commit`; re-running `provision-claim.yaml` by hand does not work (`gh pr create` fails with `main` as head) and `hydrate-github-claim.yaml` alone keeps the old pin. One case still needs a human merge: a delete of a claim whose CR is already gone stops in `delete-github-claim.yaml` at `Fail if any pull request could not be created` and leaves its claims PR open. That proves the mechanism, not the next org: keep reading `org-before.json`, `org-after.json` and `org-diff.txt` next to the verdict, and report anything surprising.

- **No org named.** Each of these runs offline and needs no approval. Run `$V/drive.sh --label ob-defaults-list-noorg --expect-exit 1 -- defaults list` and the same for `defaults show component`, `defaults apply ComponentClaim-my-api`, `discovery map`, `preflight --kind repo --name my-api --create` and `edit ComponentClaim-my-api --description x --diff`. Each exits 1 with `--org or FSCRT_ORG is required`. With `--expect-exit 2`: `watch-checks ComponentClaim-my-api` (`--org or FSCRT_ORG is required`) and `delete component my-api` (`--org or FSCRT_ORG is required even in dry-run mode to validate the claim exists`). `features list my-api` exits 1 with `GITHUB_TOKEN is required`. `net.log` is empty for all of them.
- **Guards.** Run `$V/drive.sh --label ob-commit-refused -- delete component my-api --commit` and `$V/drive.sh --mode read -- kinds`. Both exit 2 before any CLI runs; the first prints `ERROR: --commit needs --mode write with an explicitly named pre org`.
- **Read the org.** Run `$V/drive.sh --mode read --org ORG --label ob-discovery-map -- discovery map --json` (also `discovery org-elements --json`, `defaults list --json`, `defaults show component`). `stdout.txt` holds the org's data. `org-diff.txt` says `no change in fs-forge branches, PRs or workflow runs`, `net.log` lists the GitHub hosts reached (`blocked: false`) and the verdict is PASS. A diff, or a token in the evidence, makes it exit 4.
- **Preflight.** Run `$V/drive.sh --mode read --org ORG --label ob-preflight -- preflight --kind repo --name <name> --create --json`. `stdout.txt` is the JSON verdict for that name; `org-diff.txt` shows no change. `--edition` also takes `--old-name <current name>`; `--deletion` checks that the claim exists; `--scope claims|provider|all` limits what is checked.
- **Watch checks.** Run `$V/drive.sh --mode read --org ORG --label ob-watch -- watch-checks <Kind>-<name> --current --json` for a claim whose rendered CR in the state repo carries `firestartr.dev/last-state-pr` (bootstrapped claims without that annotation return `"status": "error"` with `lastStatePr: null` and exit 1). `--current` reads the CR from the state repo's main branch and reports its last PR status, then returns. Without `--current` the command polls the claim's PR checks until they finish or `--timeout <seconds>` (default 1800) runs out, so give it a short `--timeout` in a drive. A PR with no registered checks returns `no_checks` immediately (exit 1), without polling for registration. Registration waiting belongs only to the post-provision mutation watch described below. `--current` remains a point-in-time read and can report `no_checks`.
- **Edit and features reads.** Run `$V/drive.sh --mode read --org ORG --label ob-edit-diff -- edit <Kind>-<name> --description x --diff --json` and `... -- features list <component> --json`. Without `--commit` they read the claim from the org and print the result; `org-diff.txt` shows no change.
- **Delete dry run.** Run `$V/drive.sh --mode read --org ORG --label ob-delete-dry -- delete <kind> <existing-name>`. `stderr.txt` says `Dry run — would dispatch unprovision-claim.yaml with:` and lists `claimType`, `claimName`, `includeVariants` and `waitForClaimChecks`; `org-diff.txt` shows no new workflow run. For a name that does not exist the command exits 2 with `Claim not found`. The dry run read the org's claims map, so `net.log` is not empty.
- **Write: publish a claim.** After the user approves this drive, run `$V/fixture.sh setup --org ORG --id <id>` and then the `create` commands it prints. For a group:
  `$V/drive.sh --mode write --org ORG --label ob-create-group -- create group --name fsf-verify-grp-<id> --description "fs-forge verification" --type business-unit --profile.displayName fsf-verify-grp-<id> --providers.github.name fsf-verify-grp-<id> --providers.github.org ORG --providers.github.privacy closed --annotations.json '{"firestartr.dev/ia-test":"true"}' --commit`.
  `org-diff.txt` shows a new branch `fs-forge/GroupClaim-fsf-verify-grp-<id>` in `ORG/claims` and a new `provision-claim.yaml` run; the workflow then opens PRs in `state-github` and `state-infra`, so `statePrs` grows too. Read the PR and run state in the org before reporting.
- **Write: edit an existing claim.** After the user approves this drive, run `$V/drive.sh --mode write --org ORG --label ob-edit-commit -- edit <Kind>-<name> --description "<new description>" --commit` for a claim that already exists in `ORG/claims` and has no live `fs-forge/<Kind>-<name>` branch. `edit --commit` republishes the mutated claim down the create path, so `org-diff.txt` shows a new branch `fs-forge/<Kind>-<name>` and a new `provision-claim.yaml` run, and `statePrs` grows as the workflow opens PRs in `state-github` and `state-infra`. `cleanup.sh` does not remove remote leftovers; the branch and any PRs stay until the user removes them or a delete write drive runs.
- **Write: add, edit or remove a Feature.** Features republish the mutated `ComponentClaim` the same way. After the user approves each drive, run `$V/drive.sh --mode write --org ORG --label ob-features-add -- features add <component> --name <feature> --version <version> --commit`, `... --label ob-features-edit -- features edit <component> --name <feature> --version <version> --commit` (omit `--version`/`--ref` to keep the current pin), and `... --label ob-features-remove -- features remove <component> --name <feature> --commit`, each against a ComponentClaim that exists and has no live `fs-forge/ComponentClaim-<component>` branch. Every `org-diff.txt` shows a new branch `fs-forge/ComponentClaim-<component>` and a new `provision-claim.yaml` run, and `statePrs` grows as the workflow opens PRs in `state-github` and `state-infra`. `cleanup.sh` does not remove remote leftovers; the branch and any PRs stay until the user removes them or a delete write drive runs.
- **Write: remove it again.** After a second approval, run `$V/drive.sh --mode write --org ORG --label ob-delete-commit -- delete group fsf-verify-grp-<id> --commit` for one of the claims above (or `delete component fsf-verify-cmp-<id> --commit`; `$V/fixture.sh teardown` runs both). `org-diff.txt` shows a new `unprovision-claim.yaml` run. `delete domain` has no delete route (see Gotchas); `cleanup.sh` does not remove remote leftovers, so any branch or PR stays until the deletion PR is merged. On a `claims_repo` 3.2.0 org the workflow waits for that PR's `PR Verify` and merges it itself, so both drives exit 0; on 3.0.1 it does not, and the PR is left for a human.
- **Write: audit issue.** After the user approves this drive, run `$V/drive.sh --mode write --org ORG --label ob-audit-issue -- create domain --name fsf-verify-<unique> --description "fs-forge verification" --owner group:<an existing group> --annotations.json '{"firestartr.dev/ia-test":"true"}' --commit --create-issue`. `stdout.txt` ends with a JSON line carrying `issue` and `pr`. `org-diff.txt` shows the claims PR on `fs-forge/DomainClaim-fsf-verify-<unique>` as merged and a successful `provision-claim.yaml` run; it does not track issues, and the branch is gone after the merge. Read both with `gh`: the PR's author is the token's user and its body is `Closes #<n>`, and the issue is closed with the run URL as a comment. For `delete <kind> <name> --commit --create-issue`, the CLI closes the issue itself once the unprovision run succeeds; with `--no-wait` it stays open.
- **Proof.** Report each drive with its `org-diff.txt`. A read drive passes only when it holds the line `no change in fs-forge branches, PRs or workflow runs`; any `diff` output fails it. A write drive whose diff is empty fails with exit 4; otherwise it passes only when the diff shows exactly the branch, PRs and runs the command promised, and the org state you read afterwards agrees.

## Gotchas

- `delete` without `--commit` is a dry run of the dispatch only: it still needs `--org` and the token, it reads the claims map and it fails on an unknown claim.
- `edit REFERENCE` and `features add|edit|remove <component>` without `--commit` read the org, so they are `read` drives, not offline ones. `edit --json` needs `--diff` or `--show-defaults`.
- Every `--commit` mutation publishes on the shared branch name `fs-forge/<Kind>-<name>`, so a claim whose branch is still live (for example right after an `ob-create-commit` on the same claim) is refused with `Branch already exists: ...`. Delete the branch or pick another existing claim before republishing.
- In `read` and `write` mode an `--org` inside the fs-forge arguments must equal the drive's `--org`; a different org is refused.
- On a busy pre org other people's branches, PRs and runs change the diff. A diff that names something your drive did not create is a false positive; record it and rerun.
- Provisioning is asynchronous. `org-diff.txt` right after the drive may not yet show the state-repo PRs; take `org-snapshot.sh snap ORG after.json` again later and `org-snapshot.sh diff` against the drive's `org-before.json`.
- For `create`, `edit` and `features add|edit|remove --commit`, verify the default check watch after provisioning: `stderr.txt` must name the reconciliation PR and report `All checks passed` only on success. If provisioning already merged the wet PR, compare the watched identity against the rendered CR's `firestartr.dev/last-state-pr` on the state repo's default branch, including YAML block-scalar (`|` or `>`) values. The watch downloads that default branch once and filters YAML locally, avoiding per-manifest API reads and finding newly committed CRs before GitHub code search indexes them. Check every configured state repo: an open PR in one must not suppress a merged PR's checks in another. Compare both head-commit and merge-commit checks when their SHAs differ; a successful plan on the head must not hide a failed apply on the merge commit. If the reconciliation commit (merge SHA when available, otherwise head) has no checks yet, the watch must keep polling or time out. Successful merge-only checks must pass without requiring checks on a distinct head SHA. For a cleanup PR, it must watch the `last-state-pr` redirect rather than the cleanup PR's checks. `--no-wait-for-checks` opts out; `--no-wait` skips both waits. These paths require an approved write drive; offline help and refusal drives do not prove their execution.
- The `ia-test` annotation is used here as well as by other skills: `$V/fixture.sh setup` writes `firestartr.dev/ia-test: "true"` on the two claims a write run creates, and `smoke-test-renderer` uses it for test claims. `rollout-functionality` goes through `firestartr-operation` and never uses fs-forge-cli directly. Use this skill when `fs-forge` is itself under test.
- `--path` on `create` only matters for TFWorkspaceClaim and SecretsClaim.
- `create --commit` builds the claim from its flags and the schema defaults only: the org's `.config/claims_defaults.yaml` is not merged, so a field the defaults list sets still has to be a flag (`GroupClaim` `providers.github.privacy`, `ComponentClaim` `providers.github.branchStrategy.name`). `$V/fixture.sh setup` prints create commands whose output equals its seed for that reason.
- `--issue` and `--create-issue` only work with `--commit` and exclude each other; `--issue-title`/`--issue-body` need `--create-issue`. `--issue` rejects a missing number or a pull request number before any write. On failure the CLI best-effort comments the error on the audit issue, whether created or adopted; it reopens the issue only when the workflow was already dispatched.
- `unprovision-claim.yaml` routes only claim types with a delete workflow; `delete domain|system ... --commit` dispatches anyway and the run fails with `Unknown claim type`. Prove the delete side of `ob-audit-issue` on a kind it routes (group, user, orgwebhook, component, tfworkspace, secrets).
- Deleting a claim whose CR is already gone cannot finish: `delete-github-claim.yaml` skips the CR PR, fails `Fail if any pull request could not be created`, and `unprovision-claim.yaml` never reaches `Merge claims PR`, so the deletion PR stays open (`fail` at `Wait for delete workflow`). Delete while the CR is still live, or merge that leftover PR by hand.
- After a `claims_repo` upgrade, `provision-claim.yaml`'s `Open or reuse claim PR` can read its own just-created PR back as nothing and the next step dies with `PR_NUMBER: 0` and `no pull requests found`. Redispatch the same workflow on the same `fs-forge/<Kind>-<name>` ref once: with the PR now visible it runs end to end.
